# Architecture and deliberate boundaries

## Deployable edge path

Browser keyword -> same-origin Worker -> fixed YouTube `search.list` and `videos.list` endpoints -> public metadata -> official IAB taxonomy + Jev HTTP API -> video-level result JSON. Search automatically classifies new candidates in sequence. If `fallback_required` is true, subtitle input in the video detail panel follows the existing per-segment path. Successful reclassification retains previous outputs in `previous_results`; a failure or cancellation leaves the current output unchanged.
Static HTML/CSS/ES modules and the Worker are deployed together with Workers Static Assets. No database, GPU, model weights, Node native modules or subprocesses are needed by the Worker entrypoint. Server data stays in memory; there are no transcript logs or analytics. TypeSafe receives either normalized public metadata or selected text segments. Thumbnail pixels are not fetched or analyzed.

## Local path

The Node server reuses the same Worker handler and adds a Python extraction adapter. It binds to 127.0.0.1, validates Host/Origin, bounds body sizes, and allows at most two concurrent POST handlers. Python is started with execFile arguments (no shell), a 45-second process timeout and bounded stdout. YouTube, Jev, Gemini keys and the legacy App token are removed from its environment. Do not expose the localhost adapter through a public tunnel.

YouTube extraction is optional and may be blocked. The cloud path intentionally does not attempt it. A local extraction JSON can be uploaded into the hosted UI; no local service URL is accepted by the Worker.

## Inference contract

Noul per subject provides multi-label decisions rather than mutually exclusive Choice probabilities. Breadth is bounded, so this is a budgeted hierarchical search, not exhaustive classification of every leaf. Parent-to-child scores are independently evaluated; minimum-path scoring is a heuristic only. Inconsistency is flagged rather than hidden. Absence of sufficient evidence and exhaustion of compute budgets are different statuses.

No vision encoder, OCR, ASR or VLM is implemented. Metadata is a fast-path estimate, not proof of video contents. The next quality study needs human-labeled videos and separate metrics for metadata-only coverage, fallback rate, hierarchical precision/recall, calibration, latency and end-to-end cost.

## Topic and purpose discovery

Selected IAB topics use configurable AND/OR matching over accepted labels and their actual ancestor IDs. Viewing-purpose selections use OR, intersected with the topic group and assessment-state filter. Counts and filters cover only collected candidates. Any active topic, purpose, or assessment-state filter pauses automatic pagination; resuming clears the filters. JSON exports retain the selected filter configuration and all collected items.

Five project-defined purposes (introduction, tutorial, product comparison, news, case study) are independent Noul questions batched with separate topic- and purpose-evidence sufficiency checks. They are not IAB categories and are never inferred from category names. Each evidence unit retains raw values, accepted labels, evidence IDs and purpose sufficiency in `purpose_assessment`. Top-level `purpose_rubric` records version, threshold, evidence scope, catalog definitions and discovery provenance. Classification output is schema `1.3`; collection exports are `explore-1.2`.

Insufficient purpose evidence suppresses accepted purpose labels while retaining scores; topic sufficiency is independent. No accepted purpose is not itself proof that the catalog is incomplete. Short or budget-skipped segments and legacy results remain explicitly unassessed. Purpose results obtained before a later IAB budget limit remain usable. For transcripts, the UI aggregates accepted purposes only from assessed segments and leaves omitted segments unknown. The keyless demo uses explicit purpose fixtures; no live error substitutes demo data.

`POST /api/purposes/discover` sends at most 20 normalized public metadata records and existing definitions to the fixed Gemini `generateContent` endpoint. `GEMINI_API_KEY` remains server-side; `GEMINI_MODEL` is server-configured. There are no tools, grounding searches or arbitrary URL fetches. One request has a 45-second timeout, 4,096 output-token cap and 256 KiB response cap. Gemini 2.5 thinking is limited to 512 tokens so it does not consume the entire JSON output allowance. JSON Schema and application validation constrain at most four proposals per request/eight additions per search. The model selects server-provided evidence IDs; the server resolves these to original title/description excerpts, without asking the model to reproduce quotations. Referenced IDs must be in the current sample. Semantic synonym merging is model-assisted, with exact normalized-name deduplication. Neither quoted text nor candidate correctness is thereby independently verified.

The first completed batch with purpose abstentions triggers discovery once. New catalog definitions are appended without changing existing definitions, assigned content-derived IDs and given a catalog version. All collected results with valid resume state then evaluate only missing purposes; later search pages reuse the same catalog. Manual discovery prioritizes previously unsampled records. Empty proposals, failures and cancellation preserve the current catalog/results; retry resumes unfinished purpose evaluation before discovering more definitions. Generation history is exported. Existing IAB classifications remain unchanged by a purpose-only refinement.

## Resuming classification

`POST /api/classification/refine` accepts a server-signed checkpoint, an optional signed purpose catalog, an action (`purposes` or `continue`) and a 4/12-attempt budget. Domain-separated HMAC-SHA256 uses the server Jev secret to authenticate client-held state; rotating it invalidates state. Tokens expire after six hours, are size bounded and excluded from JSON exports. They contain evidence and are **signed, not encrypted**; they are not access-control credentials. No mutable server-side session cache is required. Taxonomy checksum/version/size and rubric versions must match; client-supplied raw scores or unsigned definitions are never accepted. Oversized checkpoints leave the classification usable with an explicit continuation-unavailable reason. A checkpoint lineage is bounded to 40 evaluation runs; this is not a per-user rate limit.

The checkpoint stores the original normalized evidence, raw per-node/per-purpose scores, catalog and evaluation-run provenance. A continuation reconstructs hierarchy scores from the signed raw values and asks Jev only about unevaluated nodes. Initial branch/depth limits are replaced by a request call/time budget on continuation; relevance pruning still applies, so it is not exhaustive evaluation of all taxonomy nodes. Eligible unvisited roots/children remain explicit pending IDs. Completed prior rows survive budget exhaustion. Browser cancellation or an upstream error preserves the last completed response; work in the interrupted request may be billed and is not checkpointed back to the client. Omitted transcript segments remain omitted. Branch exhaustion alone no longer recommends captions; low/no metadata confidence still does.

## Deployment threat model

There is no application-token authentication. Search, purpose discovery and explicit refinement actions invoke inference; the original classify routes retain the `consent: true` API field. POST handlers check Origin, Sec-Fetch-Site and JSON content type. These checks constrain browser cross-origin requests; they are not user authentication and do not prevent direct HTTP clients. Deployment access control (for example Cloudflare Access) and per-user limits are separate and have not been configured by this UI change. YouTube, TypeSafe and Gemini keys remain server-side, and upstream bodies are never echoed on error. Network destinations are fixed; validated parameters cannot change their origins. Defaults cap attempts, time, input size and search breadth.
